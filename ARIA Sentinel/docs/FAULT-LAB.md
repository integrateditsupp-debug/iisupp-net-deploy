# ARIA Sentinel fault lab

Two labs check one rule: **in Autonomous mode, ARIA advises three times, then acts.**

> In Autonomous mode, when ARIA finds a problem it can fix, it tells you first — 3 times, 3 minutes apart. If nobody
> answers, it fixes the problem on its own after a 10-second countdown you can cancel, through the same safety checks
> as every fix. Problems that need administrator rights or a person are never fixed on their own: after 3 unanswered
> notices ARIA tells your IT contact instead. Every notice lets you choose Fix now, Not now (waits 4 hours) or Never
> for this.

(That paragraph is what Settings → Autonomy → **Tell me first** shows; it is generated by `ruleSentence()` in
`src/shared/advisory-escalation.mjs` from the same constants the code runs, and follows the two numbers you set there.)

| | Simulated lab | Real-Windows lab |
|---|---|---|
| Where | any machine, inside `node tests/run-all.mjs` | a **test** Windows 10/11 machine, by an operator |
| What runs | the real `src/main/main.mjs` on a simulated Windows machine (`tests/lib/fault-lab.mjs`) | the installed ARIA Sentinel build, on real Windows |
| Faults | all 17 (L1, L2, L3) | 5 reversible L1/L2 faults only |
| Proves | every path of the rule: notices, cadence, the three choices, Ctrl+Alt+K, pause, restart, auto-fix, IT contact | that the real watchers, notices and escalation behave the same on a real machine, and that nothing else changes |

## The simulated lab

```
node tests/advisory-escalation.test.mjs      # the pure rule (cadence, choices, kill, freeze, restart)
node tests/fault-lab-autonomous.test.mjs     # every fault down the no-answer path + every person choice
node tests/fault-lab-modes.test.mjs          # every fault × manual/confirmed/autonomous × fresh/trusted → docs/MODE-BEHAVIOUR-MATRIX.md
node tests/fault-lab-soak.test.mjs           # 200 seeded sequences of 1–6 faults (SOAK_SEED=<n> reruns one)
node tests/advisory-ui.test.mjs              # the globe card, Home rows, chat line, Settings → Autonomy, bridge slice
node tests/fault-lab-run.test.mjs            # the real-Windows lab's safety + verdict logic (it cannot run here)
```

The simulated machine interprets exactly the commands the executor and the recipes send (an unknown command is a
test failure, not a silent success), models administrator rights honestly (a standard token gets the real
"Cannot open … service" error; UAC can be approved, denied or time out), keeps a virtual clock (40 minutes run in
milliseconds), and snapshots/diffs its state so every fix is checked against the exact keys it may change.

Faults are L1 (reversible, user level), L2 (service / network) and L3 (administrator / irreversible / red).
What each fault does in each mode is in **[MODE-BEHAVIOUR-MATRIX.md](MODE-BEHAVIOUR-MATRIX.md)** — generated by the
modes test on every run, never edited by hand.

`tests/fault-lab-defects.test.mjs` drives each defect the lab found (routing, the network guide, the DNS verify, the
disabled service, the clock check) through the real `detectIssue` path, and `tests/vendor-vetted-green.test.mjs` pins
the trust rule below.

### Which fixes may run on their own on a new install (the vendor floor)

"Advise three times, then act" needs a fix ARIA is allowed to run unattended. The execution policy
(`src/main/dry-run-policy.mjs`) allows that from **Tier 1** — which a recipe used to reach only after **10 locally
vetted runs** on this device. On a fresh install every recipe had 0, so the third unanswered notice always ended with
"tell the IT contact": the rule could never complete for a new customer. The exact rule now:

1. A recipe is **vendor-vetted** when it ships in the registry (`src/shared/recipes.mjs`) and is **green** (in
   `EXECUTABLE_RECIPES`: reversible, no confirm, no restore point), ships a **gating verify probe** (`VERIFY_GATES`: a
   read-only probe whose exit code is the verdict, so a fix that did not take ends `not_resolved`), and declares its
   **rollback / inverse** (`ROLLBACK_PLANS`) — `isVendorVetted()` in `src/shared/recipe-runner.mjs`.
2. `vettedTier()` treats the shipped catalogue as the **floor for green only**: a vendor-vetted green recipe is never
   below Tier 1, from its first run. Today that is `dns-fail-v1` and `svc-dhcp-stopped-v1`.
3. **Yellow** never takes the floor — it still needs 10 locally vetted runs (and is never run on its own anyway).
   **Red** never runs on its own at all.
4. The **local counters stay**: a verified live run is +1, a veto / abort / not-resolved run is −1; 100 local runs still
   reach Tier 0, and the counters still gate yellow.
5. **No other gate moves**: the supervisor, the 10-second countdown, Ctrl+Alt+K, the restore point for yellow,
   needsAdmin (a fix that needs administrator rights is still never run unattended — `svc-dhcp-stopped-v1` still goes to
   the IT contact in Autonomous) and red-never-automated.

So on a fresh install in Autonomous mode, `stale-dns` now gets 3 notices and then the fix (countdown first, then a
verify that really resolves a name); a fix that needs administrator rights still gets 3 notices and then the IT contact;
a green fix without a gating verify (`svc-dnscache-stopped-v1`) is still "not yet vetted" and goes to the IT contact.

### When the check after a fix fails: `not_resolved`

The runner reads a verify probe's exit code only (never its output). `dns-fail-v1` now resolves the name Windows' own
connectivity sensor resolves (`dns.msftncsi.com`, DNS only, the configured resolver — the same name the network watcher
probes), so it fails unless a resolver is reachable and answering; `svc-dhcp-stopped-v1` checks the service is Running
and a DHCP lease is present. When every step ran but that check fails, the outcome is **`not_resolved`** — never
"success", never "fixed and verified": the verification row and the FIX row say "not resolved", the run counts −1 locally,
and in Autonomous the item goes to the IT contact through the escalation path (no approval to re-run the same fix).
A third-party anchor (TCP/53 to a public resolver) was deliberately not used: corporate firewalls often block direct
external DNS, which would make every verify on those networks a false "not resolved". `ipconfig /registerdns` is a
**non-fatal** step: if Windows refuses it, a WARN row says so and the flush + cache clear still count.

## The real-Windows lab

`scripts/fault-lab.ps1` is the only thing that touches the machine. `scripts/fault-lab-run.mjs` drives it and watches
Sentinel through the local bridge (`GET http://127.0.0.1:37841/state` — the public, content-blind slice: notice
numbers, status words, outcome words and the counts of ADVISORY / AUTO-FIX / ESCALATE audit rows; never a title, a log
line or a path). Nothing leaves the computer.

### What it injects (for real, reversibly)

| Fault | Level | What the lab does | Recipe that answers | Snapshot keys it may change |
|---|---|---|---|---|
| `spooler-stuck` | L1 | pauses the *Microsoft Print to PDF* queue, then stops the Print Spooler | `svc-spooler-stopped-v1` | `services.Spooler.Status`, `printers.*` |
| `audio-stopped` | L1 | stops Windows Audio | `svc-audiosrv-stopped-v1` | `services.Audiosrv.Status` |
| `wu-stopped` | L2 | stops Windows Update (only if it is running) | `svc-wuauserv-stopped-v1` | `services.wuauserv.Status` |
| `bits-stopped` | L2 | stops BITS (only if it is running) | `svc-bits-stopped-v1` | `services.BITS.Status` |
| `temp-bloat` | L1 | writes about 200 MB under `%TEMP%\aria-fault-lab\` | `disk-low-space-v1` | `temp.labBytes` |

`spooler-stuck`, `audio-stopped`, `bits-stopped` and `temp-bloat` are the same faults (same ids, same recipes) as in the
simulated lab. `wu-stopped` is real-only: the simulated `wu-stuck` is a *hung* update, which cannot be produced
reversibly.

### What it refuses — simulated only

| Fault | Why it is never injected on a real machine |
|---|---|
| `stale-dns` | L1 — would change DNS |
| `time-drift` | L1 — would change the clock |
| `teams-stuck` | L1 — would close an app and reset its cache |
| `wu-stuck` | L2 — a hung update cannot be produced reversibly (`wu-stopped` stops the service instead) |
| `wlan-stopped` | L2 — would disconnect the network |
| `dnscache-stopped` | L2 — would change DNS |
| `dhcp-lease-stale` | L2 — would change the network |
| `spooler-disabled` | L3 — would change a service startup type |
| `system-files-corrupt` | L3 — simulated only |
| `bitlocker-recovery` | L3 — simulated only |
| `winsock-corrupt` | L3 — would change the network stack |
| `print-driver-crash` | L3 — simulated only |
| `dhcp-stopped` | L2 — would change the network |

The script never changes the network, DNS, the registry, the clock, a default app or a service's startup type, and
never writes outside its own folders (`%TEMP%\aria-fault-lab\` for the junk, `%TEMP%\aria-fault-lab-state\` for its
snapshots and log). `tests/fault-lab-run.test.mjs` scans every command in the script to keep it that way.

### The commands

```
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\fault-lab.ps1 -List
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\fault-lab.ps1 -Snapshot
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\fault-lab.ps1 -Inject <id|id,id|all>
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\fault-lab.ps1 -Verify
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\fault-lab.ps1 -Restore
```

- **-Snapshot** (read-only): services (status + startup type), the lab printer's queue, the default apps for common
  file types and links, the IP configuration (adapter state, addresses, gateway, DNS servers, DHCP), the lab folder's
  size, the total size of `%TEMP%` and the system drive's free space → `snapshot-baseline.json`. While an injection is
  live the baseline is kept and the new snapshot is saved beside it.
- **-Inject**: asks Windows for administrator approval (UAC) when a service is stopped, records what each service was
  before, then injects. A service that is not running is left alone and recorded as "nothing to inject".
- **-Verify**: a fresh snapshot, compared with the baseline. Keys a live fault may change are *intended*; `%TEMP%`'s
  total size, the system drive's free space and the print-job count move on their own and are *volatile* (reported,
  never judged); **any other difference fails the verify (exit 1)**. After **-Restore** nothing is intended, so the
  verify then checks that the machine is back to its baseline.
- **-Restore** (always safe; UAC): starts only services that were running before the lab stopped them, resumes only
  the queue the lab paused, deletes only `%TEMP%\aria-fault-lab\`. It never stops or reconfigures anything. Running it
  twice is harmless. With no record it restores from the baseline; with neither it only starts stopped Automatic lab
  services (what Windows does at the next boot anyway).

Exit codes: 0 ok · 1 an unintended change, or a restore step failed · 2 bad usage / not Windows / no guard / UAC
declined · 3 refused (a simulated-only fault). Every step is logged to `%TEMP%\aria-fault-lab-state\fault-lab.log`.

**The excluded folder.** Every path the script reads, lists or writes is checked against the app's own rule, read at
run time from `src\shared\path-guard.mjs`, plus the folders the person excluded in the app. If the rule cannot be read
or fails its self-test, the script refuses to run (fail closed). A folder that matches is skipped before it is listed,
and junctions are never followed.

### The operator's run — click by click

1. Use a **test** Windows 10/11 machine (never a customer's), signed in as the person who uses it; keep an
   administrator account at hand for the UAC prompts.
2. Start the ARIA Sentinel build under test and leave it running (the globe visible).
3. **Settings → Mode**: choose **Autonomous**.
4. **Settings → Autonomy & contacts → Live fixes**: ON. **Autonomy level**: Full-auto (tick "I understand") — Safe-auto
   also works for these green fixes; Approve-first and Observe do not take the rule.
5. **Tech contacts**: add one line (`name, email, phone, admin`) → **Save**. (A business device without one is held at
   Approve-first.)
6. **Tell me first**: *Minutes between notices* = **1** → **Save**. The sentence above the field must now read "3 times,
   1 minute apart".
7. Open PowerShell (**not** as administrator) in the `ARIA Sentinel` folder and run:
   `node scripts/fault-lab-run.mjs --faults all --minutes 10`
   (`--dry-run` prints the plan and touches nothing; `--faults spooler-stuck,audio-stopped` runs a subset.)
8. Approve the UAC prompt when the faults are injected, and again when they are restored.
9. **Do not answer the notices** — the run measures the no-answer path. (A second, attended run is useful too: run
   `--faults spooler-stuck` and click **Fix now** on notice 2 — Windows asks for administrator approval and the spooler
   restarts through the same supervised pipeline, countdown first.)
10. Read the verdict: `dist\FAULT-LAB-<YYYY-MM-DD>.json` (and the log above).

### What to expect on a real machine

| Fault | Expected |
|---|---|
| `spooler-stuck`, `audio-stopped` | Within about a minute of the stop (the service watcher checks every 60 s): notice 1 of 3 on the globe card, on Home and in ARIA chat, plus a desktop notification; notices 2 and 3 a minute apart; then the IT contact is told and the fix waits as an approval. **Never** an AUTO-FIX row: these fixes need administrator rights, which ARIA never uses unattended. |
| `wu-stopped`, `bits-stopped` | On most machines these start Manual (trigger-start), so stopped is their normal idle state and the watcher stays quiet — **no notice is the correct result**. Where one is set to Automatic, it behaves like the spooler. |
| `temp-bloat` | 200 MB is far from the 5%-free threshold on a normal disk: **no notice** is expected. If the disk really is that full, the clean-up needs administrator rights → 3 notices, then the IT contact. |

The verdict passes when every fault behaved as expected, no AUTO-FIX row appeared during the run, the verify while the
faults were live found nothing outside the intended keys, and the verify after restore found the machine back at its
baseline.

**What the real lab cannot show.** None of the faults that may be injected for real is a user-space, vetted green fix,
so the last step of the rule — *fixed on its own after three notices* — is proven only in the simulated lab
(`stale-dns`, on a fresh install and on a trusted device). The real lab proves the other half on real Windows: the
notices, the cadence, the escalation, and that nothing is changed without a person.

### The verdict file

`dist\FAULT-LAB-<date>.json` (a second run the same day gets `-2`, `-3`, …) holds the plan, the expectation for each
fault (computed from what the service's startup type was before injection), what was observed (notice count, track,
status words, outcome word, seconds to first notice and to the end), the ADVISORY / AUTO-FIX / ESCALATE audit-row
deltas, and both verifies. Service, printer, temp and disk values are kept; network and default-app values are reduced
to "changed" so the file stays content-blind.

## Gaps the labs found (reported, not hidden)

These are listed in MODE-BEHAVIOUR-MATRIX.md with the exact scenario; none of them is papered over by the tests.

Closed on 2026-10-14 (each with a test in `tests/fault-lab-defects.test.mjs` / `tests/vendor-vetted-green.test.mjs`):

- ~~**Wrong recipe for a stopped DHCP Client.**~~ `SYSTEM.SERVICE.STOPPED.DHCP` matched the clock-drift guide
  (`system-time-drift-v1`). It now routes to `svc-dhcp-stopped-v1` (restart the DHCP Client — administrator rights, so
  never unattended — verified by "service Running + lease present"). Lab fault: `dhcp-stopped`.
- ~~**No recipe for a dropped network.**~~ `NET.ADAPTER.DOWN` and `NET.DOWN` now route to `net-adapter-down-v1`, a guide
  (Airplane mode off, Wi-Fi / Ethernet back on, cable and adapter, restart the adapter in Settings → Network) — never a
  command.
- ~~**"Verified" can be wrong for DNS.**~~ `dns-fail-v1` has a gating verify (above): after a stale lease or a corrupt
  Winsock catalog it now ends **not resolved** and the IT contact is told, instead of "fixed and verified".
- ~~**"Advise three times, then act" never completes on a fresh install.**~~ The vendor floor (above).
- ~~**A Disabled service is silent.**~~ A watched service that Windows needs running (not one of the idle-normal
  Manual / Trigger-Start services such as Windows Update or BITS) that goes from Running to Stopped **with its start type
  set to Disabled** now raises the stopped-service signal with `startType: "disabled"`: the card says "Print Spooler is
  disabled (start type), not just stopped — needs an administrator", and it routes to the service recipe as needs-admin —
  never automatic (no recipe changes a start type, so the restart a person may approve fails honestly until an
  administrator re-enables the service). A service already disabled when the watcher starts stays quiet, like every
  edge-triggered signal.
- ~~**No clock-drift watcher.**~~ The perf watcher runs a read-only clock check every 15 minutes (declared in the spawn
  budget; the 5-second CPU / memory sampling stays native): it reads the offset Windows' own time service last computed
  against its NTP source — the *Windows Time Service › Computed Time Offset* performance counter (microseconds, absolute;
  Windows 10 1607+), through its WMI class `Win32_PerfRawData_MicrosoftWindowsW32TimePerf_WindowsTimeService`
  (property `ComputedTimeOffset`). A child PowerShell prints one number; nothing is resynced, no NTP server is contacted
  by ARIA, the time source's name is never read. Beyond 2 minutes it emits `SYSTEM.TIME.DRIFT` once per excursion →
  `system-time-drift-v1` (a guide). No reading (counter absent, time service stopped) is "unknown", never drift.
  `w32tm /query /status` was not used: its text is localised and it may be refused to a standard token. **To confirm on a
  real machine**: the class and property names come from Microsoft's counter documentation and the
  prometheus-community windows_exporter issue #532, not from a run on Windows here.

Still open:

- **DNS Client cannot be restarted from a session.** `svc-dnscache-stopped-v1` refreshes the resolver, which fails
  while the service is down; a reboot or a person is needed (it fails honestly).
- **A stale lease needs an administrator.** The DNS refresh cannot renew a lease (`ipconfig /renew` needs administrator
  rights), so `dhcp-lease-stale` ends not resolved and goes to the IT contact; the network guide reaches the person.
- **`Clear-DnsClientCache` may need elevation.** `ipconfig /registerdns` is non-fatal now (a refusal is a WARN row); if
  Windows also refuses `Clear-DnsClientCache` to a standard user (the strict-administrator model), `dns-fail-v1` fails at
  that step on every unattended run — only its flush changes anything. The registry declares both steps user-space. To
  confirm on a real machine.
